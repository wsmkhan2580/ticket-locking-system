# Prompts.md — AI Usage & Implementation Notes

This document is a transparent record of how AI was used to build this
project, per the brief's documentation requirements.

---

## 1. AI tool used

**Claude** (Anthropic), used as a pair-programmer/architect through a single
detailed specification prompt describing the full feature (backend
architecture, frontend architecture, UI/UX direction, color system,
concurrency requirements, sprint structure, deployment, and documentation
requirements).

## 2. What AI was used for

- **Entire initial codebase generation**: the backend (Express + Socket.IO +
  in-memory lock manager) and frontend (React + Vite + Tailwind +
  shadcn-style components + Socket.IO client) were both generated by Claude
  from the specification prompt in one pass.
- **Architecture decisions**: how to split lock-ownership logic into a
  single `LockManager` class so there is exactly one code path that can
  mutate the lock table (see Section 4, "Important implementation
  decisions").
- **Documentation**: this file and `README.md` were drafted by Claude,
  describing the actual code produced rather than generic boilerplate.
- **UI/UX and visual system**: color tokens, typography, glassmorphism
  restraint, and animation timing were implemented directly from the
  brief's explicit specification (exact hex values, "200ms ease-in-out",
  Inter typography), not left to arbitrary AI aesthetic preference.

## 3. What was NOT AI-generated / requires human follow-up

The brief calls for a few deliverables that involve accounts, external
services, or a physical recording — those cannot be produced by an AI text
generation pass and are the responsibility of whoever deploys this project:

- **Actual deployment** to Vercel/Netlify (frontend) and Render (backend).
  The code, environment variable wiring, and CORS handling needed for a
  successful deployment are implemented and documented in `README.md`
  Section 9, but creating the accounts, connecting the repo, and clicking
  "Deploy" is a manual step.
- **The dual-window demo video.** This requires screen-recording two live
  browser windows against a running deployment (or local dev servers) and
  is inherently a manual/human deliverable.
- **`npm install`** in both `backend/` and `frontend/` has not been run as
  part of generating this project — dependencies are declared in each
  `package.json` but need to be installed in your own environment before
  running the app.
- Any project-specific values you should fill in yourself: the deployed
  frontend/backend URLs in `README.md` Section 9, and your own display name
  when using the app.

## 4. Important implementation decisions

- **Single source of truth for locks.** All lock state lives inside one
  `LockManager` instance (`backend/src/lock/lockManager.js`), which is the
  only module allowed to read or write the lock `Map`. Socket event
  handlers only ask it questions ("can this agent lock this ticket?") and
  broadcast the result — this was chosen specifically to make the
  concurrency guarantees easy to reason about and to keep the ownership
  check in exactly one place, rather than scattered across event handlers.
- **Reverse index for fast disconnect cleanup.** `LockManager` also keeps
  `agentTickets: Map<agentId, Set<ticketId>>` so that on disconnect it can
  release exactly the tickets that agent held, without scanning every
  ticket in the system. At this scale a full scan would also be fine, but
  the explicit index makes the intent ("release only what this agent
  owned") unambiguous in the code.
- **Rejections don't broadcast.** When a lock/unlock request is rejected
  (already locked, not the owner, etc.), only the requester receives a
  `lock_error` event. Nothing is broadcast to other clients, because from
  their perspective nothing changed. This avoids noisy, meaningless
  updates across the room.
- **REST is for static data only; Socket.IO is for state.** The one REST
  endpoint (`GET /api/tickets`) exists purely so the frontend can do a fast
  initial fetch of ticket metadata. Lock state itself is only ever
  communicated over Socket.IO (`locks:snapshot` on connect, plus
  `ticket_locked`/`ticket_unlocked` broadcasts) — there is intentionally no
  REST endpoint that can mutate a lock, so there is exactly one code path
  for lock mutations to reason about concurrency against.
- **Agent identity vs. lock ownership are kept separate.** An agent's
  display name (`agentName`) is client-supplied and purely cosmetic. Actual
  lock ownership is tied to the server-assigned `socket.id`, so a client
  cannot claim ownership of someone else's lock by sending a different name
  — the server never trusts client-asserted identity for authorization
  decisions.
- **CORS origins are environment-driven from the start**
  (`backend/src/config/cors.js` reads `CLIENT_ORIGINS`), specifically so
  that moving from local development to the Render/Vercel deployment
  requires only an environment variable change, never a code change — per
  the brief's "do not leave production configuration dependent on
  localhost" requirement.
- **shadcn-style primitives were hand-written** (`Button`, `Badge`, `Card`
  in `frontend/src/components/ui/`) rather than scaffolded via the shadcn
  CLI, since this environment couldn't run an interactive installer. They
  follow the same conventions (a `cn()` class-merge utility, `cva` for
  variants) so they would slot into a real shadcn/ui project without
  structural changes.
- **Toasts and presence count are optional enhancements**, included because
  the brief explicitly listed them as optional (not mandatory) — they were
  kept intentionally small and are not load-bearing for the core locking
  behavior.

## 5. Manual review notes

All generated code should be read and understood — in particular:

- `backend/src/socket/socketHandlers.js` and `backend/src/lock/lockManager.js`
  together define the entire concurrency model; understanding these two
  files is enough to explain the whole locking mechanism in an interview
  setting.
- `frontend/src/hooks/useTicketSocket.js` is the single place where the
  frontend subscribes to server events and mutates local React state —
  useful to review to confirm the frontend never invents lock state on its
  own.

Before submitting, run both apps locally with two browser windows (see
`README.md` Section 7) to confirm the real-time behavior matches the
acceptance criteria, and adjust copy, seed ticket data, or styling to match
your own portfolio's voice if desired.
